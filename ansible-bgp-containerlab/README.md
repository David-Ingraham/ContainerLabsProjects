# BGP Lab with ContainerLab and Automation

Network automation lab demonstrating BGP and multicast configuration between FRR and GoBGP routers using Ansible and gRPC. Supports multiple network topology designs.

## Prerequisites

- Docker installed and running
- Python 3.x (for create_links.py)
- Access to containerlab image (ghcr.io/srl-labs/clab)
- Platform support:
  - Linux/macOS: scripts/shell/bash/setup.sh
  - Windows: scripts/shell/ps/setup.ps1 (PowerShell)

## Network Designs

The lab supports multiple network topology designs, selectable via command-line argument:

| Design | Description | Use Case |
|--------|-------------|----------|
| `og` | Original design with FRR1, FRR2, GoBGP1, multicast branch | Default, demonstrates BGP + multicast |
| `linear` | Linear chain of routers | Simple forwarding path |
| `hub-spoke` | Central hub with multiple spokes | Star topology |
| `branch-tree` | Branching tree structure | Hierarchical networks |
| `multi-source` | Multiple multicast sources | Complex multicast scenarios |

Each design has corresponding topology and inventory files in `containerlab/topologies/` and `ansible/inventories/`.

## Credentials Management

### credentials.env (required, gitignored)

Create this file at `ansible/credentials/credentials.env`:

```
FRR_ROOT_PASS=<root-password>
FRR_USER=<ansible-username>
FRR_PASS=<ansible-password>
```

This file is:
- Used at image build time to bake credentials into the FRR Docker image
- Sourced by setup scripts to generate credentials.yml
- Listed in .gitignore (not committed to version control)

### credentials.yml (auto-generated)

The setup scripts generate `ansible/credentials/credentials.yml` from credentials.env:

```yaml
ansible_user: <value-from-FRR_USER>
ansible_password: <value-from-FRR_PASS>
```

## Components

### FRR Container Image

Defined in [docker/Dockerfile.frr](docker/Dockerfile.frr):

- Base image: frrouting/frr:latest
- BGP, Zebra, and PIM daemons enabled
- SSH server installed and configured
- Ansible user created with vtysh shell
- Credentials baked in at build time

### Automation Container

Defined in [docker/Dockerfile.automation](docker/Dockerfile.automation):

- Base image: python:3.11-slim
- Python packages: ansible, grpcio, grpcio-tools, protobuf, netmiko, paramiko
- Ansible collections: frr.frr, ansible.netcommon
- GoBGP gRPC stubs compiled from proto files

### Multicast Client Containers

**Sender** ([docker/Dockerfile.m_cast_sender](docker/Dockerfile.m_cast_sender)):
- Python 3.11 Alpine base
- Runs `multicast_sender.py`
- Sends UDP packets to multicast group 239.1.1.1:5000
- Configurable TTL, periodic transmission

**Receiver** ([docker/Dockerfile.m_cast_receiver](docker/Dockerfile.m_cast_receiver)):
- Python 3.11 Alpine base
- Runs `multicast_receiver.py`
- Joins multicast group via IGMP
- Receives and displays multicast packets

### Topology Definitions

Topology files in `containerlab/topologies/` define:

- Management network (10.1.1.0/24)
- All container nodes with management IPs
- FRR runtime initialization (SSH, FRR daemons, PIM daemon)
- GoBGP with gRPC API on port 50051
- Design-specific node arrangements

### Inventory Configuration

Inventory files in `ansible/inventories/` contain:

- Lab name (used for dynamic container references)
- Router-to-router link definitions (point-to-point subnets)
- Backend network definitions (host subnets)
- BGP parameters (AS numbers, router IDs, neighbors)
- PIM configuration (interfaces, RP address)

- Multi-neighbor support for FRR routers

### Data Plane Setup

[scripts/python/create_links.py](scripts/python/create_links.py) reads inventory files and:

- Accepts `-d` design flag for dynamic inventory selection
- Creates Docker networks for each subnet
- Connects containers to appropriate networks with assigned IPs
- Configures default routes on host containers
- Enables IP forwarding on routers
- Verifies connectivity between routers

### BGP and Multicast Configuration Playbook

[ansible/playbooks/config_playbook.yml](ansible/playbooks/config_playbook.yml):

**BGP Configuration:**
1. Configures GoBGP via Python gRPC script (if present in design)
2. Configures FRR routers via Ansible frr.frr.frr_bgp module
3. Supports multiple BGP neighbors per router
4. Applies route-maps for route exchange
5. Verifies BGP session establishment and routing tables

**Multicast Configuration:**
1. Enables PIM on specified interfaces
2. Configures RP address (statically assigned)
3. Enables IGMP on receiver-facing interfaces
4. Verifies PIM neighbors, interfaces, and RP info

## Setup Process

The setup scripts perform:

1. Parse design argument (default: og)
2. Source credentials.env and generate credentials.yml
3. Build Docker images if not present:
   - network-automation:latest
   - frr-ansible:latest
   - multicast-sender:latest
   - multicast-receiver:latest
4. Clean up existing containers and networks
5. Deploy ContainerLab topology (design-specific)
6. Wait for container stabilization
7. Configure data plane networks (create_links.py -d DESIGN)
8. Enable IP forwarding and add static routes on GoBGP (if present)
9. Copy configuration files to automation container
10. Extract lab name from inventory for dynamic container references

### GoBGP Kernel Routing

GoBGP is a BGP daemon only - it does not install routes into the kernel. The setup scripts run an Alpine container in GoBGP's network namespace to:

- Enable IP forwarding: `sysctl -w net.ipv4.ip_forward=1`
- Add static routes: `ip route add 10.1.0.0/24 via 10.0.1.2`

### Multicast Verification

```bash
./scripts/shell/bash/verify-multicast.sh
```

Checks multicast configuration:

- PIM neighbors on all routers
- PIM interface status
- RP information
- IGMP groups on LHR
- Multicast routing table (mroute)
- PIM state

### Expected End State

**BGP:**
- All BGP neighbors in Established state
- Route exchange:
  - FRR1 learns 10.3.0.0/24 from GoBGP1
  - FRR1 learns 10.2.0.0/24 from FRR2
  - FRR2 learns 10.1.0.0/24 and 10.3.0.0/24 from FRR1
  - GoBGP1 learns 10.1.0.0/24 from FRR1
- All connectivity tests pass

**Multicast:**
- PIM neighbors established between FRR1 and FRR2
- RP configured on all routers (pointing to FRR1)
- IGMP enabled on FRR2's receiver-facing interface
- Receivers can join multicast groups
- Multicast traffic flows from source through FHR to LHR to receivers


### Common Issues

**Docker reserves .1 for gateway**: When creating Docker networks, .1 is reserved for the bridge gateway. Use .2 for router gateway IPs.

**GoBGP no shell**: The GoBGP image contains only the daemon. Use `docker run --network container:clab-{LAB_NAME}-gobgp1 alpine sh -c "..."` to run commands in its namespace.

**BGP not advertising routes**: A router can only advertise networks it has in its routing table. Verify the interface is connected and has the correct IP.

**Multicast not forwarding**: Verify PIM neighbors are established, RP is configured correctly, and IGMP is enabled on receiver-facing interfaces. Check `show ip mroute` for active multicast routes.

**No IGMP membership**: Ensure receivers are actually joining the multicast group. Check `show ip igmp groups` on the LHR.

## Multicast Technical Notes

### Protocol Overview

**PIM (Protocol Independent Multicast):**
- Builds multicast distribution trees
- Operates independently of unicast routing protocol (hence "protocol independent")
- Uses unicast routing table for RPF (Reverse Path Forwarding) checks
- BGP provides the unicast routing information PIM needs

**IGMP (Internet Group Management Protocol):**
- Used by hosts to join/leave multicast groups
- Routers listen for IGMP membership reports
- LHR uses IGMP to discover which receivers want which groups

**RP (Rendezvous Point):**
- Meeting point for multicast sources and receivers
- FRR1 acts as RP in this topology
- Statically configured (alternative: BSR for dynamic RP election)

### Multicast Roles

- **FHR (First Hop Router)**: frr1 - closest to the multicast source (host1)
- **LHR (Last Hop Router)**: frr2 - closest to the receivers
- **RP**: frr1 - rendezvous point for PIM tree building

### Multicast Tree Building

1. Receiver joins group (IGMP membership report)
2. LHR (frr2) sends PIM Join toward RP (frr1)
3. Source sends multicast traffic
4. FHR (frr1) encapsulates and sends to RP (itself in this case)
5. RP forwards down the distribution tree to LHR
6. LHR forwards to receivers on local network

### Why BGP Matters for Multicast

BGP provides the unicast routing table that PIM uses for:
- RPF checks (ensuring multicast traffic arrives on the correct interface)
- Determining the path toward the RP
- Building the most efficient multicast distribution tree

Without proper unicast routing from BGP, PIM cannot correctly build multicast trees.
